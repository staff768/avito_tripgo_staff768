# Trip Service

Сервис поездок TripGo: создаёт поездку, отдаёт её и завершает. Данные в
PostgreSQL, схема накатывается миграциями, создание и завершение поездки
атомарно пишут в две таблицы.

Лабораторная работа 1: HTTP API и PostgreSQL.

## Запуск

Нужны Go 1.27 и `tripgoctl` — он поднимает PostgreSQL и генерирует `.env`.

```bash
tripgoctl cluster start
tripgoctl environment start
tripgoctl connect          # генерирует .env с адресом PostgreSQL

make migrate               # накатить миграции
make run                   # запустить сервис
```

Конфигурация только из окружения, `.env` в git не попадает. `DATABASE_URL`
обязателен: без него сервис падает на старте. Если PostgreSQL недоступен, сервис
тоже не стартует — на старте выполняется `Ping`.

## API

| Метод | Путь | Ответы |
|---|---|---|
| `POST` | `/api/v1/trips` | `201`, `400`, `409`, `500` |
| `GET` | `/api/v1/trips/{tripId}` | `200`, `400`, `404`, `500` |
| `POST` | `/api/v1/trips/{tripId}/finish` | `200`, `400`, `404`, `409`, `500` |
| `GET` | `/health` | `200` |
| `GET` | `/ready` | `200`, `503` |

Источник истины — `contracts/openapi/trip-service.openapi.yaml`, типы и серверные
интерфейсы сгенерированы из него (`make generate`) и руками не правятся. Ручки
работы 3 (`/positions`) есть в контракте и пока отдают `501`.

Ошибки — по RFC 9457 в `application/problem+json`, клиент смотрит на `code`:

| HTTP | `code` |
|---|---|
| `400` | `invalid_request` |
| `404` | `trip_not_found` |
| `409` | `trip_completed` |
| `409` | `driver_busy` |
| `500` | `internal_error` |

Успешные ответы — `application/json`. `/health` и `/ready` отдают `HealthResponse`
и в успешном, и в ошибочном случае.

```bash
curl -sS -X POST localhost:8080/api/v1/trips \
  -H 'content-type: application/json' \
  -d '{"user_id":"5cb72c04-7650-45c9-a79b-bcdba0631e0c",
       "driver_id":"8860b315-ec86-42eb-a17c-7c163d721ff5",
       "start_point":{"latitude":59.9398,"longitude":30.3146},
       "end_point":{"latitude":59.9290,"longitude":30.3626},
       "price":1450}' | jq

curl -sS localhost:8080/api/v1/trips/$TRIP_ID | jq
curl -sS -X POST localhost:8080/api/v1/trips/$TRIP_ID/finish -i
```

## Решения

### Уровень изоляции — `read committed`

Задаётся при старте транзакции в `Do` (`internal/postgres/txmanager.go`).

Инварианты держит сама бд: двух активных поездок у водителя не даёт уникальный
индекс, двойного завершения — условие `status = 'active'` в `UPDATE`. Более
строгий уровень ничего не добавляет, а `repeatable read` на тех же конкурентных
сценариях давал бы ошибки сериализации `40001`, которые пришлось бы ретраить,
иначе клиент получал бы `500` вместо `409`.

### Менеджер транзакций

```go
type TxManager interface {
    Do(ctx context.Context, fn func(ctx context.Context) error) error
}
```

- `Do` открывает транзакцию, кладёт её в `context` по приватному ключу и
  вызывает `fn` с обогащённым контекстом;
- `fn` вернула `nil` → `COMMIT`; вернула ошибку → `ROLLBACK` и проброс исходной
  ошибки; паникнула → `ROLLBACK` в `defer` и `panic` дальше;
- откат идёт с `context.WithoutCancel`: при уже отменённом контексте запроса
  откатывать было бы нечем;
- вложенный `Do` видит транзакцию в контексте и просто вызывает `fn`, вторую не
  открывает;
- репозиторий берёт исполнителя запроса из контекста (`Executor(ctx)`): есть
  транзакция — работает через неё, нет — через пул. Транзакция не передаётся
  аргументом метода, поэтому вызов репозитория вне `Do` тоже работает — это
  автокоммит на соединении из пула.

Бизнес-код в `internal/service` знает только про интерфейс с методом `Do`, `pgx`
в него не протекает. Создание поездки внутри одного `Do` делает `INSERT` в
`trips` и запись перехода в `trip_status_history`, завершение — `UPDATE` и вторую
запись. Если вторая вставка падает, в `trips` не остаётся ничего.

### Запрет двух активных поездок на водителя

```sql
CREATE UNIQUE INDEX trips_driver_active_uidx ON trips (driver_id) WHERE status = 'active';
```

`SELECT` перед `INSERT` тут не помогает: при одновременных запросах оба пройдут
проверку раньше, чем любой вставит строку. Индекс отклоняет вторую вставку на
уровне бд, приходит код `23505`, репозиторий узнаёт его по имени индекса и
отдаёт доменную ошибку, транспорт — `409 driver_busy`, а не `500`.

### Защита от двойного завершения

```sql
UPDATE trips SET status = 'completed', finished_at = $1, updated_at = $1
WHERE id = $2 AND status = 'active' RETURNING ...
```

Между проверкой статуса и записью нет окна: из двух одновременных `finish`
строку обновит один, второй получит ноль строк, `finished_at` не
перезаписывается. Ноль строк означает «поездки нет» либо «уже завершена» — их
различает дополнительное чтение, чтобы отдать `404` или `409`.

### `/health` и `/ready`

`/health` отвечает, пока жив процесс, и в бд не ходит: по нему оркестратор
решает, не пора ли перезапустить контейнер, и падение бд не должно приводить к
рестарту пода. `/ready` пингует бд с таймаутом `DATABASE_QUERY_TIMEOUT` и отдаёт
`503`, если она недоступна: по нему инстанс убирают из балансировки.

### Прочее

- Цена — целые рубли в `bigint`, float для денег не используется.
- Валидация тела идёт до бизнес-логики: неизвестные поля запрещены, обязательные
  проверяются на наличие, `user_id` и `driver_id` — непустые UUID, координаты в
  допустимых диапазонах, `price >= 0`.
- `id`, `started_at` и `finished_at` задаёт сервис, из запроса не принимаются.
- Текст ошибки бд наружу не отдаётся: клиент получает `internal_error`,
  подробности уходят в лог.
